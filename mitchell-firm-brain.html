Reliability requirements to validate

  • Recoverable job state. Confirm what survives a restart today; the target is independent page state so one failure never loses completed work.
  • Retry policy. Observe the real failure modes first. A proposed baseline is up to three attempts with backoff before escalation.
  • Evidence package. Validate the required output: full-page files, SHA-256 hash, capture time, and source URL.
  • Matter filing. Confirm the CRM write path, tags, and indexing delay before promising same-minute search.
  • Visible failure handling. Agree who gets notified, what context they receive, and who owns recovery. No silent drops is the acceptance standard.

Put the firm in control of its data and access

Target operating model

The target operating model keeps the firm in control of its case files, CRM, memory, accounts, and keys. The technical review determines today’s actual topology; the stabilization scope then closes any ownership, retention, or access gaps it finds.

Inside the privilege boundary

Firm-controlled target
  • CRM + case files — existing data and runtime mapped first, with backup and restore requirements documented before changes.
  • Document index — target outcome: the approved file types are searchable with page-level citations and a measurable refresh interval.
  • The brain’s memory — target outcome: voice notes and working preferences remain portable and under firm control.
  • Audit log — target outcome: who asked what, which documents were read, and what was approved for sending can be exported.
  • Keys & secrets — inventoried during review, then moved into firm-controlled storage where needed.

External services to constrain

Requirements to confirm
  • Language models — target contract: send only the passage needed, disable retention and training where supported, and keep providers replaceable.
  • Email — target workflow: use the firm’s Microsoft 365 authorization and log approved sends to the matter.
  • Web capture — target boundary: fetch only public pages without disclosing matter context in the request.
  • Supio — stays exactly where it is for document review. The brain can point to it, never replaces it.

Continuity before Josh’s move

Target · before Oct 1

The first objective is continuity, not feature expansion: understand the current system, agree on what “reliable” means, and remove single-person operating risk. Timing, scope, and price are set only after the technical review.

Step 1 · Audit

Read the build

  • Walk Josh’s handoff files and code with him
  • Map integrations, runtime, data, accounts, and access
  • Collect the commands that fail most often
  • Document risks, scope options, and an informed estimate
Step 2 · Stabilize

Fix the critical path

  • Prioritize the failures Jesse feels in daily litigation
  • Add appropriate recovery, logging, and alerts
  • Replay real commands before shipping changes
  • Start with web capture if the review confirms it as the top issue
Step 3 · Maintain

Keep it dependable

  • Run the system with agreed reliability evidence visible
  • Record the handoff and operating procedures
  • Place ownership and support responsibilities in writing
  • Give Jesse one accountable support path
Step 4 · Extend

Add what earns priority

  • Evaluate intake auto-briefing after stabilization
  • Rank “what’s due this week” and other matter workflows
  • Extend voice capture from Jesse’s actual habits
  • Scope each addition against measurable value

What we’ll ask for on Friday

  • Read access to the code and Josh’s handoff notes (no keys needed yet; NDA first if you prefer)
  • A date for a one-hour handoff call with Josh before he moves
  • Three recent examples of the assistant failing, in your words
  • Who else at the firm should be able to talk to the brain

Options set after technical review

  • The review produces the options — current-state map, risk ranking, success criteria, timing, and price.
  • A bounded stabilization project may follow if the critical path is clear; a proof of value is an option only if it is the better fit.
  • Ongoing maintenance is proposed after the support load, ownership gaps, and operating cadence are known.
  • Firm control — ownership, access, handoff, and exit terms are documented in any proposal.
